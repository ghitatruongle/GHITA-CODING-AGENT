🎯 Mục tiêu tổng quan

Xây dựng ứng dụng GHITA CODING AGENT — một desktop AI agent hoàn chỉnh, tích hợp nhiều dự án open-source để tạo thành một sản phẩm thống nhất. Ứng dụng có thể đưa lên GitHub như một dự án open-source, cho phép cộng đồng đóng góp.

Mục tiêu cuối cùng: Một app desktop (Win/Linux) + mobile (Android), code bằng TypeScript, tích hợp 15+ dự án open-source, sẵn sàng cho production.

📦 Danh sách dự án open-source tích hợp

Các dự án dưới đây được tham khảo và tích hợp vào GHITA CODING AGENT. Refer projects thực tế nằm trong refer_project/ gồm 7 nhóm: ai-core, ai-framework, ai-tools, browser, desktop, infra, memory. Mỗi dự án phục vụ một vai trò cụ thể trong kiến trúc tổng thể.

🛡️ Zero Bug Implementation Protocol

🔹 Nguyên tắc vàng (Golden Rules)

1. Read Before Write
Không bao giờ edit code khi chưa đọc hiểu file gốc. Luôn đọc ít nhất 50 dòng xung quanh vùng sửa.
2. TypeScript Strict Mode
strict: true trong tsconfig. Không dùng any, // @ts-ignore, as any.
3. Test Trước Khi Commit
Mọi code mới phải có unit test. Mọi bug fix phải có regression test. Chạy test trước push.
4. Handle All Errors
Không có catch-all empty. Mọi try/catch phải log lỗi và thông báo cho user. Network error phải có retry.

// packages/shared/src/utils/platform.ts export type Platform = 'windows' | 'linux' | 'android' | 'ios'; export function getPlatform(): Platform { if (typeof window !== 'undefined' && window.__TAURI__) { // Tauri desktop const os = window.__TAURI__.os; return os.platform === 'win32' ? Pairing với desktop, background/foreground, đổi mạng Wi-Fi/4G, khóa màn hình, mở lại; ghi nhận reconnect time và trạng thái UI.

Ngày 4 — Adverse conditions

Giả lập mạng chậm, packet loss, disk gần đầy, CPU cao, mất quyền ghi file; xác nhận app thất bại có kiểm soát.

Ngày 5 — Upgrade and rollback

Nâng cấp từ bản cũ, kiểm tra migrate dữ liệu; sau đó rollback về bản cũ để chắc dữ liệu không bị phá vỡ một chiều.

Ngày 6 — Regression replay

Chạy lại toàn bộ bugs đã từng gặp trong known issues database; xác nhận không bug nào tái phát trên cả 3 nền tảng.

Ngày 7 — Release candidate sign-off

Tổng hợp metrics, so sánh với baseline, đóng toàn bộ blocker/critical/high không có workaround; chỉ khi đó mới tag release.

5. Observability và crash forensics bắt buộc

Hạng mục Yêu cầu thực hiện Kết quả mong đợi
Structured logging Mọi log phải có timestamp, sessionId, platform, feature, severity, errorCode. Khi user báo lỗi có thể truy ngược 1 phiên làm việc cụ thể.
Crash boundary Desktop React có ErrorBoundary; mobile có global JS error handler và native crash collector. App không chết âm thầm, có màn hình fallback và log rõ.
Network tracing Socket connect/disconnect/retry phải được log; timeout phải có mã lỗi riêng. Phân biệt được lỗi server, lỗi mạng, lỗi client state.
Performance counters Thu CPU/RAM/fps/reconnect time ở các flow chính trước release. Phát hiện sớm memory leak, lag tích lũy, stream giật.
Bug reproduction template Mỗi bug ghi đủ: bước tái hiện, expected, actual, log excerpt, build version, platform. Bug fix nhanh hơn và giảm bug "không tái hiện được".

6. Quy trình triage bug và SLA hotfix

Mức độ Ví dụ SLA xử lý Hành động
Blocker App không mở, pairing fail toàn bộ, mất dữ liệu < 4 giờ Dừng release ngay, rollback hoặc phát hành hotfix cùng ngày
Critical Crash ngẫu nhiên ở flow chính, ANR lặp lại, leak API key < 12 giờ Freeze merge tính năng mới, chỉ ưu tiên fix và regression test
High Tính năng chính chạy không ổn định theo nền tảng < 24 giờ Fix trước mốc release; nếu chưa fix xong phải feature-flag tắt
Medium UI lỗi nhẹ, retry chậm, log thiếu thông tin 1-3 ngày Cho vào sprint hiện tại, thêm test chống tái phát
Low Copy text, spacing, icon, wording Backlog Gom xử lý theo batch, không chặn release nếu không ảnh hưởng flow chính

7. Checklist sign-off cuối cùng

  • Có ít nhất 2 máy Windows, 2 máy Linux, 2 thiết bị Android test ra kết quả giống nhau cho các flow chính.
  • Có ít nhất 1 vòng test trên Android emulator và 1 vòng trên Android máy thật.
  • Đã kiểm tra cả first install, upgrade, rollback, offline, network flap, sleep/resume, background/foreground.
  • Tất cả bug blocker/critical/high đã đóng hoặc feature liên quan đã bị tắt bằng feature flag.
  • Regression suite của mọi bug vừa fix đã được thêm vào test automation hoặc checklist manual bắt buộc.
  • Log sản phẩm không còn error mới xuất hiện lặp đi lặp lại sau 24 giờ beta nội bộ.
  • Bản phát hành có changelog nội bộ, danh sách known limitations và kế hoạch rollback rõ ràng.
  • Người kiểm thử khác người viết tính năng đã xác nhận pass, tránh tự test rồi tự duyệt một mình.
Điều kiện để tuyên bố bản release đủ ổn định dùng hằng ngày
Chỉ khi tất cả release gates đều PASS, soak test 7 ngày không phát sinh blocker/critical, metrics ổn định so với baseline, và toàn bộ flow chính trên Windows, Linux, Android đều có bằng chứng test lặp lại. Nếu thiếu một trong các điều kiện này, bản build chỉ được xem là beta/internal build, không phải release ổn định.

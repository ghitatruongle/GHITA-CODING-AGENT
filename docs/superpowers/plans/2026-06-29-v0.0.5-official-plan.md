# 0.0.5 Official Release — Master Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **🚫 COMMIT POLICY (user-imposed):** The executing agent MUST NOT run `git commit`, `git tag`, or any other write to git history. All changes are left in the working tree; the user reviews and commits manually. Release artifacts (tags, GitHub Releases) are also created by the user, not the agent.

**Goal:** Ship GHITA Coding Agent **0.0.5** (drop `-beta` suffix) with all 44 audit fixes, 5 Q3 2026 features with full UI integration, iOS build verification, and full release artifacts.

**Architecture:** Big-bang single release. Three sequential waves (W1 security baseline → W2 desktop + 3 features → W3 mobile + 2 features + iOS). Each wave exits with a working buildable branch (`release/0.0.5`). After W3, the release is tagged and published.

**Tech Stack:** Turborepo + pnpm 11.5, TypeScript 5.6, React 18, Tauri 2, Rust, React Native 0.76, Kotlin, Vitest 3.2, Recharts, react-flow, Web Speech API.

- Create or push tags
- Create GitHub Releases

## §7 What to do if a wave fails

If a quality gate fails after a wave:

1. **Identify the failing task** from the sub-plan.
2. **Revert that task's changes** (the user can `git checkout` specific files, or the agent can show what to revert).
3. **Fix forward** — re-implement without breaking tests.
4. **Re-run the failing gate.**
5. **Do NOT proceed to the next wave** until the current wave is green.

If a single audit fix is fundamentally blocking (e.g., requires Rust compiler update), mark it P3 in CHANGELOG and document the deferral reason in the spec. The release can still ship with 43/44 fixes if the remaining one has a clear path forward.
